## 二、问题逐条详解

### P1｜分块不生效：23 个 chunk 被切成 3 个大段（致命，根问题）

**现象**

知识库原文用 `## HR-001 员工年假`、`## FIN-002 交通报销` 这类标题明确划分了 23 个独立条款。但导入系统后，实际被切成了 **3 个大段**（每段约 1000–1200 字）：

| 段落 | 包含的 chunk | 主题 |
|------|-------------|------|
| 段 A | `hr_001`~`hr_005` + `fin_001`（6 个） | HR 全部 + 差旅住宿 |
| 段 B | `fin_002`~`fin_005` + `it_001`~`it_004`（8 个） | 报销 + IT |
| 段 C | `prod_001`~`prod_004` + `cs_001`~`cs_003` + `sec_001`~`sec_002`（9 个） | 产品 + 客服 + 安全 |

**证据**

- 知识库原文共 7430 字节，含 23 个 `##` 二级标题（`## 使用说明` 之外共 23 个条款标题）；
- 检索返回的 source 只有 3 个，每个 source 内部按顺序包含 6 / 8 / 9 个条款内容；
- 3 段边界恰好对应原文按字节数截断的位置，与 `##` 标题位置**不一致**。

**根因**

系统导入 Markdown 时**没有把 `##` 二级标题识别为分块边界**，而是走了默认的固定字符数切分（约 1000–1200 字/段）。`HR-001` 这类自定义 ID 只存在于标题文字里，系统既没当成 chunk_id，也没当成分隔符。

**影响**

1. **检索粒度太粗**：一段里混着 6~9 个互不相关的条款。问"年假"会把差旅住宿标准一起召回，问"云盘容量"会把退款规则一起召回；
2. **chunk 级命中率无法计算**：23 个 chunk 全被包进 3 段，只要整篇返回，chunk 级"软命中"必然是 100%，测不出真实水平；
3. **引用定位困难**：无法告诉用户"答案来自哪一条"，只能定位到"哪一章"。

**修复建议**

1. **首选**：在平台的 RAG/分块设置里，把 Markdown 分块分隔符配置为 `##`（或开启"按标题切分"选项），重新导入；
2. **备选**：把 `test_knowledge_base.md` 按 `##` 标题拆成 23 个独立 `.md` 文件（或按 README 建议的 `{id, text, metadata}` 结构化方式）逐条导入，每个文件即一个 chunk；
3. 导入后先验证：随机挑 2~3 条问题看返回的 source 数量是否 ≈ 文档数、每条是否只含单个条款。

### P2｜全量返回：每条问题都返回全部 3 段（严重）

**现象**

35 条 query 中，**段 A / 段 B / 段 C 各自出现了整整 35 次**——也就是每条问题都把 3 段全部返回，只是排列顺序不同。

**证据**

```
段A 出现次数：35（=全部 query）
段B 出现次数：35
段C 出现次数：35
```

**根因**

系统当前 Top-K（召回条数上限）≥ 文档片段总数（3），等价于"全量召回 + 只排序"。即检索环节退化为：**对全部内容算一遍相关性，排个序，然后全部交给模型**。

**影响**

1. **Hit@2 / Hit@3 ≡ 100%**：因为永远返回全部段，这俩指标失去任何区分度，看起来"满分"，实际毫无意义；
2. **上下文浪费**：每次问答都塞进约 3500 字的全部知识库内容，token 成本高，且无关段落会稀释模型注意力；
3. **质量风险**：真实检索中，排在后面的低相关段落可能被模型误当作依据使用。

**修复建议**

1. 调小 Top-K（目标：返回 3~5 个 **chunk**，而不是 3 个大段；在修复 P1 之后调整才有意义）；
2. 确认平台是否有 `top_k` / `chunk_size` / `max_results` 类参数可传（本次测试请求中未携带，走的是服务端默认值）。

### P3｜段间语义混淆：2 条问题 Top-1 未命中（中等）

**现象**

32 条有答案的问题中，30 条正确段落排在第 1 名；**2 条（q010、q019）正确段落被挤到第 2 名**，排第一的是语义"长得像"的错误段落。

**证据**

| 问题 | 期望 | 实际排名 | 为什么混淆 |
|------|------|---------|-----------|
| q010「去一线城市出差，酒店每晚最多报多少？」 | 段A（含 `fin_001` 差旅住宿） | 段B（报销类）第 1 | 问题里的"报多少"（报销语义）与段B 里 fin_002~fin_005 整段的报销主题高度重合，把真正的"差旅住宿标准"（fin_001，被归入 HR 段A）压到第 2 |
| q019「密码输错几次会被锁定？锁多久？」 | 段B（含 `it_003` 账号解锁） | 段C（安全类）第 1 | "密码/锁定"与安全主题（sec_001 数据访问、sec_002 安全事件）语义相近，段C 整体得分压过了含 `it_003` 的段B |

**影响**

如果系统直接取 Top-1 喂给 LLM 生成回答，这两类问题会**引用错误段落**、给出错误出处，甚至答错。q010/q019 都是日常工作高频问题类型，不能忽略。

**根因**

1. **粗分块放大混淆**：段B 里 8 个条款挤在一起，"报销"主题权重被放大；段C 里 9 个条款里安全语义密集。若按 23 个条款独立切分，混淆面会大幅缩小（fin_001 单独成块后，与"酒店/城市"匹配度很高，不会再被报销段压过）；
2. **无 reranker**：纯向量相似度排序对"主题相近、细节不同"的段落区分能力有限。

**修复建议**

1. 修复 P1（分块）后重测——大概率这两条会自动恢复 Top-1；
2. 若仍不达标，加 **reranker**（cross-encoder 重排模型）对召回结果二次精排；
3. 提升 embedding 模型对"条款级"短文本的区分度（如换更大/领域适配的 embedding）。

### P4｜无答案问题 100% 误召回（中等）

**现象**

测试集包含 3 条**知识库中根本没有答案**的问题，理想行为是"返回空 / 拒答"：

| 问题 | 知识库是否有答案 | 系统行为 |
|------|----------------|---------|
| q031「公司明年会不会涨薪？」 | ❌ 无 | 返回全部 3 段 |
| q032「星河科技今年的股票代码是什么？」 | ❌ 无 | 返回全部 3 段 |
| q033「员工餐厅每天几点供应晚餐？」 | ❌ 无 | 返回全部 3 段 |

**误召回率 = 3/3 = 100%**。

**影响**

RAG 系统拿到这些"看起来相关"的段落（q031 命中 HR 段、q033 命中员工相关段）后，会**倾向于用相似内容硬编一个答案**，而不是诚实地说"知识库里没有"。这是 RAG 幻觉的主要来源之一，在客服/合规场景下风险很高。

**根因**

1. 检索只看**相对相似度排序**，不看**绝对分数**：任何问题都会有一个"最相似的段落"，系统没有做"低于阈值就拒绝"的判断；
2. 没有独立的"知识库是否包含答案"判定环节（如 LLM 判断或分数阈值门控）。

**修复建议**

1. 为检索结果设置**相关性分数阈值**：所有段落得分均低于阈值 → 返回"未找到相关信息"；
2. 增加**拒答机制**：让模型在无强相关证据时明确回答"知识库中未收录该信息"，而不是编造；
3. 把 q031~q033 这类无答案问题**长期保留在回归测试集**里，防止后续改动引入"过度自信"。

### P5｜指标失真：当前测试结果无法回答"chunk 级命中率"（连带）

**现象**

由于 P1（全部 chunk 被包进 3 段）+ P2（每问全量返回），出现两个指标假象：

1. **chunk 级软命中率 = 100%**：23 个 chunk 全在返回的 3 段里，任何问题都"命中"，完全无法分辨好坏；
2. **Hit@2 / Hit@3 = 100%**：全量返回导致后位命中恒真。

**结论**

本次测试**唯一可信的量化指标**是段落级：

| 指标 | 数值 | 说明 |
|------|------|------|
| 段落级 Hit@1 | **93.75%（30/32）** | 正确段是否排第 1 |
| 段落级 Hit@2 / Hit@3 | 100% / 100% | 无区分度，仅供参考 |
| 段落级 MRR | **0.969** | 平均倒数排名（2 条 rank2 各贡献 0.5） |
| 段落级 Recall@3 | 100% | 全量返回必然结果 |
| 无答案误召回率 | **100%** | 见 P4 |

**这意味着**：在修复 P1、P2 之前，**无法得出任何"chunk 级命中率"结论**——不是系统差到测不出，而是测量口径本身被系统行为架空了。

## 三、修复优先级与复测方案

### 修复路线（按依赖顺序）

| 优先级 | 动作 | 期望效果 |
|--------|------|---------|
| **P0** | 修复分块：配置 `##` 分隔符重导，或拆 23 个独立文件导入 | 检索单元回到条款级，chunk 级指标可算 |
| **P1** | 调小 Top-K（如 3~5 个 chunk）+ 相关性阈值 | 不再全量返回；无答案问题开始拒答 |
| **P2** | 上 reranker（或换 embedding） | 消除 q010 / q019 类段间混淆 |
| **P3** | 加拒答/无证据判定 | 无答案问题误召回率从 100% 降到 0 |

### 复测方案

1. 用**同一份** `test_queries.jsonl`（35 条）重跑，保证可比；
2. 修复后判定标准：
   - chunk 级 Hit@1 / Hit@3 / MRR 可正常计算（不再是 100% 假象）；
   - q010、q019 恢复 Top-1；
   - q031~q033 误召回率 = 0%（或至少显著下降）；
   - 无答案问题在答案质量上表现为"明确拒答"，而非编造。
3. 保留一套**不参与调参的 hold-out 测试集**（README 已建议），避免调参过拟合测试集。
