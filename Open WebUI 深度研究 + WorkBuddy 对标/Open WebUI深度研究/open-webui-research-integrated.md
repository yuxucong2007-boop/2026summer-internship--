

> 本文整合「逐功能研究」「核心功能（下）」「API 工具函数」三篇笔记，按统一格式（功能是什么 / 怎么用 / 亮点 / 不足）梳理 Open WebUI 的主要功能模块，覆盖聊天、模型管理、知识库、权限，以及 API / 工具 / 函数三类扩展能力。

## 聊天对话

**功能是什么：**用户输入问题、选择模型并持续追问的主流程。它承载文本、附件、工具、建议提示和多轮上下文。

**怎么用：**

1. 在首页输入框输入问题。
2. 确认输入框右侧当前模型。
3. 需要文件或工具时先从输入区左侧入口添加。
4. 提交后在同一会话中追问或编辑、重新生成。

**亮点：**

- 首屏直接进入对话，低认知负担。
- 当前模型常驻输入区附近，用户知道是谁在回答。
- 普通聊天能继续衔接文档、搜索、语音和记忆。

**不足：**

- 输入区入口密度高，新用户需要识别图标。
- 模型能力和实例工具开关的边界不够显性。
- 回答质量仍受后端模型、连接和上下文限制影响。

## 模型管理

**功能是什么：**负责接入和治理可用模型，包括模型来源、模型 ID、标签、连接地址、凭证和卸载等能力。

**怎么用：**

1. 管理员接入本地或 OpenAI 兼容模型服务。
2. 配置服务地址、访问凭证和模型 ID。
3. 刷新模型列表并确认模型可用。
4. 用户在聊天输入区选择模型。

**亮点：**

- 兼容 OpenAI 风格接口。
- 前端资源显示可聚合多个模型来源，并支持前缀避免重名。
- 管理配置与聊天选择分离。

**不足：**

- 配置复杂度取决于外部服务、凭证和协议兼容。
- 模型名称、ID、前缀和来源可能混淆。
- 缺少统一的速度、价格、上下文和工具能力对比。

## 多模型切换

**功能是什么：**在同一会话或任务中更换当前模型，用不同模型继续回答、重新生成或对比结果。

**怎么用：**

1. 打开输入框旁的模型选择器。
2. 选择另一个已接入且有权限的模型。
3. 用新模型继续下一轮，或对同一问题重新生成。
4. 记录模型名称、上下文和回答差异。

**亮点：**

- 切换入口靠近输入区，操作成本低。
- 适合快模型草稿、强模型复核、本地模型处理隐私数据。
- 在同一会话中保留上下文，便于复核。

**不足：**

- 切换不等于公平比较，上下文和工具状态会干扰结论。
- 不同模型可能不兼容同一工具、图片或上下文长度。
- 若不显示成本和延迟，用户难以选择。

## 流式输出

**功能是什么：**模型生成片段到达后立即渲染，用户无需等待完整答案完成。当前实例开启 WebSocket，前端存在停止任务接口。

**怎么用：**

1. 提交问题。
2. 观察回答逐步出现。
3. 方向错误或内容足够时点击停止。
4. 完成后复制、追问或重新生成。

**亮点：**

- 即时反馈，减少等待焦虑。
- 可中途止损，节省时间和 token。
- 生成、停止和错误可形成明确状态。

**不足：**

- 首 token 延迟仍然存在。
- 网络抖动可能造成断线、重复片段或 Markdown 半成品。
- 停止后的半截回答状态需要清晰语义。

## 对话历史管理

**功能是什么：**保存、定位、组织和清理聊天会话，包括历史列表、搜索、标题、标签、归档、删除和隐私控制。

**怎么用：**

1. 从左侧历史列表打开已有会话。
2. 用搜索定位旧对话。
3. 重要会话手动重命名或归档。
4. 不再需要或敏感会话执行清理。

**亮点：**

- 回访路径短，历史就在聊天左侧。
- 自动标题和标签可降低维护成本。
- 列表浏览与搜索定位分工明确。

**不足：**

- 自动标题可能含糊。
- 历史越多，侧栏越容易变成噪声。
- 删除、归档、临时聊天和服务端留存的隐私语义必须清楚。

## 知识库（RAG）

**功能是什么：**知识库是 Open WebUI 中面向文档集合的检索增强生成能力。它把用户上传的资料组织成一个可复用的知识集合，在聊天时把与问题相关的内容提供给模型，从而让模型回答组织内部资料、项目文档、产品手册或个人笔记中的问题。

它解决的是"模型原本不知道这份资料，或者资料太多无法全部放入提示词"的问题。典型链路是：

```text
创建知识库
    -> 上传文件
    -> 文本解析、切分、向量化或建立检索索引
    -> 在聊天中附加知识库
    -> 根据问题检索相关内容
    -> 将相关上下文交给模型生成回答
```

Open WebUI 的 RAG 使用方式通常可以分为三类：

| 模式 | 工作方式 | 适用场景 |
|---|---|---|
| Full Context | 尽可能把知识库内容整体注入上下文 | 文件少、内容短、需要完整上下文时 |
| Focused Retrieval | 只检索与当前问题最相关的文本片段 | 文件较多、希望控制上下文长度时 |
| Agentic Retrieval | 由模型通过检索工具决定何时搜索、搜索什么 | 需要多步查找或复杂问题时 |

核心判断不变：知识库不是简单的"上传后模型永久记住"，而是一次面向当前问题的资料检索与上下文注入。

**怎么用：**

1. 打开左侧的"工作空间"。
2. 进入"知识库"页面，点击"创建"。
3. 填写知识库名称和描述，描述应说明资料范围和使用目的。
4. 将 PDF、Markdown、文本、办公文档或其他受支持文件上传到知识库。
5. 等待文件解析和索引完成。
6. 开启一个新对话，在输入框中使用 `#` 选择知识库，或通过附件入口选择对应资料。
7. 发送问题前确认输入框附近已经出现知识库或文档标识。
8. 观察回答是否引用了正确资料；若有检索来源或上下文展开入口，应进一步核对原文。

实际使用时，建议把问题写得具体，例如：

```text
请只依据"智能风场"知识库中的资料，列出开发阶段遇到的主要问题，并按"问题、原因、解决建议"三列输出。
```

如果问题需要整份短文档的完整上下文，可以优先考虑 Full Context；如果知识库较大，则应优先使用 Focused Retrieval，并通过分段大小、重叠长度和检索参数控制结果质量。

**亮点：**

- 资料与聊天解耦：知识库建立后可以被多次对话复用，不需要每次把同一批文件重新上传。
- 适合组织化管理：名称、描述、文件数量、更新时间和来源等信息便于用户快速判断资料范围。
- 支持不同检索策略：短资料可以整体注入，大资料可以按相关片段检索，复杂任务还可以使用工具式检索。
- 知识库可作为共享资源：详情页提供访问控制入口，可以根据实例的用户、群组和权限策略管理可见范围。
- 更适合业务资料问答：相比把资料直接粘贴到聊天输入框，知识库更容易形成可维护的资料入口。

**不足：**

- 检索命中不等于答案正确：切分边界、向量模型、问题表述和模型本身都会影响结果。
- 存在上下文窗口压力：Full Context 对小文档方便，但资料变大后容易消耗大量上下文，甚至导致回答被截断或遗漏。
- 不同模式的可解释性不一致：Focused Retrieval 可能只返回少量片段，Agentic Retrieval 还会增加模型决策和工具调用的不确定性。
- 知识库内容不会自动解决权限问题：知识库的访问权限、模型权限、聊天权限和管理员权限需要分别配置。
- 原文引用仍需人工核对：如果回答没有显示可靠来源，用户不能只凭语气或格式判断模型是否真的找到了正确段落。
- 工具调用存在使用误区：使用支持原生函数调用的模型时，附加的知识库不一定会自动注入；如果检索工具没有被模型调用，回答可能没有使用附加资料。
- 大规模知识治理仍有成本：文件版本、过期资料、重复内容和不同来源的冲突，需要人工维护。

## 文档上传与处理

**功能是什么：**文档上传与处理是知识库的前置环节，负责把"文件"转换成"可检索内容"。它通常包含以下步骤：

```text
文件上传
    -> 内容抽取
    -> OCR 或媒体处理（按配置启用）
    -> 文本切分
    -> Embedding 向量化或建立索引
    -> 写入知识库
    -> 供聊天检索
```

这意味着"文件已经上传"不一定等于"已经可以高质量问答"。如果解析失败、扫描 PDF 没有 OCR、切分不合理、Embedding 模型不匹配，最终回答都会受到影响。

**怎么用：**

普通用户流程：

1. 在工作空间中创建或打开一个知识库。
2. 点击添加或上传入口，选择本地文档。
3. 等待文件状态从上传中变为可用。
4. 打开知识库详情页，确认文件名、大小或状态显示正常。
5. 在聊天中附加知识库，提出一个能够在原文中验证的问题。
6. 将回答与原文对照，检查解析结果是否保留了标题、表格、页码和关键数字。

管理员处理配置流程：

1. 进入设置中的"管理员"区域。
2. 打开"文档"设置。
3. 选择内容抽取引擎。
4. 按需要配置受支持的媒体 MIME 类型。
5. 对扫描型 PDF 判断是否启用 PDF 图片抽取和 OCR。
6. 选择 PDF 的加载模式，例如按页处理或保持跨页内容。
7. 选择文本切分器。
8. 设置 `Chunk Size`、`Chunk Overlap` 和最小合并阈值。
9. 选择 Embedding 引擎与 Embedding 模型。
10. 保存配置，再用一份小文档做检索验证。

配置时的实用判断：

| 情况 | 优先检查 |
|---|---|
| 扫描 PDF 无法检索 | OCR 是否开启，OCR 引擎是否可用 |
| 表格或版式内容错乱 | 内容抽取引擎和文档格式支持情况 |
| 回答经常缺少上下文 | Chunk Size、Chunk Overlap、Markdown 标题切分 |
| 检索速度慢或资源占用高 | Embedding 模型、文档数量、分段数量 |
| 文件上传成功但问不到内容 | 文件是否完成索引，聊天中是否真正附加知识库 |
| 多个文件主题相近且互相干扰 | 拆分知识库、改写描述、限制访问范围或调整检索策略 |

**亮点：**

- 处理链路可配置：从解析到切分再到 Embedding，管理员可以根据文档类型调整策略。
- 覆盖多种文档问题：普通文本、Markdown、PDF、图像型 PDF 和媒体文件可以使用不同处理路径。
- 可针对检索质量调参：Chunk Size 和 Chunk Overlap 让用户能够在"片段完整性"和"索引规模"之间做取舍。
- Markdown 结构可被利用：开启 Markdown 标题切分后，文档结构更容易保留，适合技术文档和知识库文章。
- 支持绕过 Embedding 或检索的高级选项：适用于特定检索后端或需要直接使用分段内容的场景。

**不足：**

- 默认配置不一定适合所有文档：同一套 Chunk Size 对说明文档、合同、代码和表格的效果可能不同。
- 解析质量依赖外部引擎：OCR、PDF 解析和媒体处理需要额外依赖，部署环境不同可能产生不同结果。
- 参数含义对普通用户不透明：用户通常能上传文件，却不容易判断切分、向量化和检索为什么失败。
- 大文件处理会消耗时间和资源：上传后的等待时间不只取决于网络，还取决于解析、OCR、Embedding 和索引规模。
- 表格、图片、页眉页脚容易丢失语义：纯文本抽取可能无法保留原文档的视觉关系。
- 重新处理会带来维护成本：修改切分或 Embedding 配置后，旧知识库是否需要重新索引，需要管理员明确验证。
- 缺少一眼可见的质量评估：仅看到"文件已上传"无法证明检索命中率、召回质量或答案准确率。

## Prompt 模板

**功能是什么：**Prompt 模板是可以被命名、复用和管理的提示词。Open WebUI 通常通过斜杠命令调用模板，例如：

```text
/review
/summarise
/postmortem
```

它把经常重复输入的任务要求固定下来，例如代码审查、文档摘要、会议纪要、事故复盘、翻译或结构化输出。

Prompt 模板和模型本身不同：

- 模型决定"由谁生成"以及模型的基础能力；
- Prompt 模板决定"希望模型如何完成任务"；
- 知识库决定"模型可以参考哪些外部资料"。

**怎么用：**

创建模板：

1. 打开"工作空间"。
2. 进入"提示词"或"Prompts"。
3. 点击"创建"。
4. 设置模板标题。
5. 设置斜杠命令，例如 `review` 或 `summarise`。
6. 编写任务说明、输出格式、限制条件和输入位置。
7. 如果需要动态内容，使用模板变量或系统变量。
8. 保存后，在聊天输入框中输入 `/`，选择已保存的 Prompt。

一个可维护的模板至少应写清楚：

```text
角色：你要扮演什么角色
任务：需要完成什么工作
输入：原文、代码、问题或上下文在哪里
判断标准：什么结果算合格
输出格式：标题、表格、JSON 或项目列表
限制：不得编造、保留数字、标记不确定信息
```

例如，一个代码审查模板可以要求模型依次检查正确性、边界条件和可读性，并规定每条问题包含文件、行号、严重级别和修复建议。

模板可以使用动态变量来减少重复粘贴，例如 `{{CLIPBOARD}}` 表示把剪贴板内容带入 Prompt。使用变量时应注意：

1. 变量名称在模板中保持一致。
2. 变量为空时，模板仍应能给出合理提示。
3. 变量内容很长时，应限制长度或先进行摘要。
4. 不要把访问令牌、密码或敏感数据写入共享模板。

**亮点：**

- 降低重复输入：常见任务可以通过短命令快速调用。
- 促进团队规范化：团队可以把输出格式、审查标准和禁用事项写进同一个模板。
- 输入入口清晰：斜杠命令比复制粘贴一大段提示词更容易被发现和复用。
- 适合沉淀工作方法：Prompt 可以成为代码审查、运营分析和文档处理流程的一部分。
- 支持动态上下文：剪贴板、用户信息、日期时间或表单输入可以让同一模板适配不同任务。
- 有利于迭代：模板列表、启用开关、分享和版本历史有助于持续维护。

**不足：**

- 模板不是效果保证：最终输出仍受模型能力、模型参数、上下文长度和外部工具影响。
- 命令容易失控：命令名称过多或命名不一致时，用户很难记忆和发现。
- 变量错误不容易排查：变量拼写、空值和格式错误可能导致模板失效或输出异常。
- 内容可能过期：团队规范、接口字段和业务规则变化后，旧模板仍可能继续被调用。
- 长输入会挤占上下文：剪贴板或文档内容没有长度限制时，模板本身的指令可能被稀释。
- 共享模板存在信息泄露风险：模板中的内部流程、敏感示例和固定指令不适合默认开放给所有用户。
- 不同模型对同一模板的执行差异明显：同一条 Prompt 在推理、代码、长文本或小模型上可能得到完全不同的输出。

## 用户角色与权限

**功能是什么：**用户角色与权限负责回答两个不同的问题：

1. **谁可以进入系统或创建账号？**
2. **进入系统后，谁可以看到、使用或管理哪些资源？**

Open WebUI 的权限体系通常包括以下层次：

| 层次 | 典型控制内容 |
|---|---|
| 认证与注册 | 登录、注册、默认用户角色、待审批账号 |
| 会话与 API 访问 | JWT 有效期、API Key 是否允许创建 |
| 目录或组织接入 | LDAP 等外部认证目录 |
| 用户和群组 | 将用户归入群组，统一分配访问范围 |
| 资源访问 | 知识库、Prompt、模型、工具等资源的可见和可用范围 |
| 管理权限 | 修改系统配置、用户、模型、文档处理和其他管理项 |

需要特别区分：关闭注册只控制"能不能自助创建账号"，并不等于已经完成知识库或 Prompt 的资源级权限隔离。

**怎么用：**

实例级认证设置：

1. 使用管理员账号进入设置。
2. 打开管理员区域中的"Authentication"。
3. 设置新用户的默认角色。
4. 设置新用户的默认群组。
5. 根据部署方式开启或关闭新用户注册。
6. 决定是否允许用户创建 API Key。
7. 设置 JWT 有效期。
8. 如果使用审批流，配置待审批账号页面显示的管理员信息。
9. 如果接入企业目录，再配置 LDAP 等外部认证方式。
10. 保存后，用普通用户和管理员账号分别验证登录及资源可见性。

资源级访问控制：

1. 创建知识库、Prompt 或其他可共享资源。
2. 在资源详情页打开访问控制入口，例如知识库详情页的"Access"。
3. 选择允许访问的用户、群组或角色。
4. 用一个没有权限的测试账号验证资源是否不可见或不可用。
5. 用有权限的测试账号验证资源仍然可以正常调用。
6. 在变更权限后检查已有会话、API 调用和共享链接是否符合预期。

最小权限建议：

- 默认新用户使用普通用户角色，不直接授予管理员权限。
- 管理员账号只用于配置和审核，不用于日常共享账号。
- 知识库和 Prompt 优先按群组开放，而不是对所有已登录用户开放。
- API Key 只在确有程序化调用需求时开启，并设置撤销和轮换流程。
- LDAP、JWT、代理层和外部身份系统的配置应一起进行安全审查。

**亮点：**

- 把认证和资源访问分层：系统登录策略与知识库、Prompt 等资源的访问策略可以分别管理。
- 支持审批式账号管理：新账号可以先进入待审批状态，再由管理员决定是否允许使用。
- 支持群组化管理：用户不必逐个配置，适合按部门、项目或客户群组授权。
- 能够控制 API 面：API Key 和 JWT 有效期设置可以降低长期凭证暴露风险。
- 可扩展企业认证：LDAP 等目录服务为组织部署提供了接入路径。
- 适合结合知识库权限：不同团队可以使用不同资料集合，减少内部文档被无关用户检索到的风险。

**不足：**

- 权限配置影响面大：默认角色、注册开关、群组和资源访问策略配置错误，可能导致越权或无法使用。
- 认证不等于授权：用户成功登录，只能说明身份被接受，不代表他有权访问所有知识库、模型或工具。
- 部署依赖较多：LDAP、反向代理、JWT、API Key 和外部模型服务的安全边界需要一起维护。
- 本地验证门槛高：没有多个测试账号时，很难完整验证"可见""可用""可管理"之间的差异。
- 共享资源的生命周期需要治理：人员离职、群组变化、项目结束后，旧权限和旧共享资源可能继续存在。
- 管理员设置的可发现性有限：普通用户不一定知道自己为什么看不到某个知识库或 Prompt。
- 审计和回溯要求较高：生产环境需要记录授权变更、API Key 使用和敏感知识库访问情况，不能只依赖页面开关。

## API 接入

**功能是什么：**API 接入让外部程序、脚本或第三方工具通过 HTTP 接口直接调用 Open WebUI 中已接入的模型能力。只需填写服务地址和 API Key 即可使用，无需本地部署模型服务，是把"聊天能力"变成"可编程能力"的桥梁。

**怎么用：**

1. 获取 Open WebUI 实例的访问地址（例如 `http://localhost:3000` 或内网/公网地址）。
2. 在「设置 → 账号」中创建 API Key，并保存密钥。
3. 在客户端（curl、Python、OpenAI SDK 等）中填入地址 + API Key。
4. 按 OpenAI 兼容格式调用接口（如 `/v1/chat/completions`）。
5. 在返回结果中处理 `content`、`usage`、工具调用等字段。

**亮点：**

- 兼容 OpenAI 接口风格，现有代码迁移成本低。
- 免本地部署模型，地址 + API Key 即填即用。
- 支持流式与非流式调用，便于做实时交互。
- 可在外部系统、脚本和机器人中复用实例上所有已接入模型。
- API Key 可单独创建和撤销，便于控制程序化访问范围。

**不足：**

- 依赖实例可用性和网络连通性，服务中断则接口不可用。
- API Key 一旦泄露风险较大，需要妥善保管并轮换。
- 接口能力、并发和限流取决于实例配置与后端模型。
- 缺少可视化界面中的模型对比信息，选型依赖外部判断。

## 工具调用

**功能是什么：**工具调用让模型在推理过程中调用外部函数或 API，从而获得实时数据或执行实际操作。同一个模型在工具调用前后的能力差距很大——以可视化图片工具为例，模型本身只能生成文本描述，而工具能把文本真正转换成图片。工具扩展了模型的能力边界，让模型从"会说话"变成"能做事"。

**怎么用：**

1. 在「工作空间」中创建或导入工具，可从开源社区下载，或让大模型生成工具代码。
2. 查看或编写工具的输入参数和返回值定义。
3. 在聊天中输入工具名称，或通过设置关联工具。
4. 模型在需要时自动发起工具调用。
5. 对比工具调用前后的输出，验证工具是否真正生效。

**亮点：**

- 大幅扩展模型能力：图片生成、实时搜索、计算、数据库查询等都能接入。
- 社区已有大量开源工具可直接复用，降低上手成本。
- 对编程能力较弱的同学，可以借助大模型本身生成工具代码。
- 工具与模型解耦，同一工具可服务多个模型，同一模型可挂载多个工具。

**不足：**

- 需要模型支持函数调用（Function Calling），非原生支持的模型效果受限。
- 工具调用失败、超时或返回格式错误会直接影响最终回答。
- 工具安全性需要审核，恶意或有缺陷的工具可能造成数据泄露或异常行为。
- 工具数量增多后，模型的工具选择可能出现偏差，需要持续调优。

## 函数（Functions）

**功能是什么：**函数（Functions）是 Open WebUI 的扩展机制，让你可以用 Python 代码无缝插手"用户提问 → 大模型推理 → 结果输出"的整个生命周期。如果把大模型比作"大脑"，那么 Functions 就是给这个大脑加上安全门禁、滤镜、自动工作流和自定义插件。

具体来说，函数可以用来实现以下几类核心应用场景：

**怎么用：**

1. 在「工作空间 → 函数」中创建函数。
2. 选择函数类型（Filter、Pipe、Action 等）。
3. 编写 Python 逻辑，实现过滤、路由或按钮动作。
4. 如需界面可调参数，定义 `Valves`（如 API 密钥、翻译语言、开关）。
5. 保存并启用函数，应用到聊天会话或作为模型下拉项。
6. 用真实对话验证函数在 Inlet / Outlet 阶段是否按预期生效。

**亮点：**

- **消息过滤与内容安全（Filter - Inlet/Outlet）**：在消息发送给模型前或返回给用户前进行拦截与修改。
  - 敏感词/脱敏过滤：自动识别身份证号、手机号、API Key 等敏感信息并掩码替换（如 `138****1234`），防止数据泄露给外部大模型。
  - Prompt 动态注入/强化：根据当前时间、用户角色或系统状态，自动给 Prompt 加上前缀或系统提示词。
  - 格式清洗与版权声明：自动统一 Markdown 格式，或在所有回答末尾挂载公司版权信息、免责声明。
- **构建"自定义模型"与智能体工作流（Pipe）**：通过 Python 代码包装出全新的"虚拟模型"，直接显示在 UI 的模型下拉列表中。
  - 多模型融合与路由：简单问题自动发给便宜的模型，复杂逻辑推理问题自动转发给更强的模型。
  - 对接非标准/私有 API：把企业内自定义 AI 服务伪装成标准模型供团队使用。
  - 复杂 Agent 工作流：结合 LangChain、LlamaIndex 或自定义逻辑，实现"搜索 → 思考 → 调用数据库 → 总结回答"的多步智能体。
- **UI 交互与快捷操作按钮（Action）**：在每条回答下方添加自定义功能按钮，例如"生成思维导图""一键翻译""转换为 Markdown 表格""朗读文本"；或一键将对话生成 PDF 发送到邮箱、同步到 Notion / 钉钉 / 飞书维基。
- **系统集成与权限/额度管理**：记录每个用户的 Token 消耗、调用频次并上报到监控系统；通过 `Valves` 让管理员或普通用户直接在界面上拉滑块、改输入框，无需修改底层 Python 代码即可改变逻辑行为。

**不足：**

- 需要 Python 编程能力，上手门槛明显高于 Prompt 模板。
- 函数代码质量需要测试，运行错误可能中断整个问答链路。
- 权限与安全配置复杂，不当开放可能引入数据泄露风险。
- 与 Pipe / 模板模型（Model）的取舍需要判断：模板模型适合固定人设和特定任务助手，无需写代码；Pipe 适合复杂逻辑处理、多模型切换、对接外部系统等场景，必须写代码。
- 函数维护成本随数量上升，版本迭代和错误排查需要专门管理。
